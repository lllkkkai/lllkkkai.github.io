## 问题的分类
1. 容器故障
2. 注册中心故障
3. 应用服务故障

### 1. 容器故障
- **Pod 频繁重启（OOMKilled）**：检查容器内存限制，使用 `kubectl describe pod` 查看原因，分析 Heap Dump
- **Pod 无法启动（CrashLoopBackOff）**：查看容器日志 `kubectl logs --previous`，检查启动脚本和配置
- **节点资源不足**：检查 Node CPU/内存使用率，确认是否触发了 Eviction

### 2. 注册中心故障
- **服务注册失败**：检查注册中心（Nacos/Zookeeper）连通性，确认网络策略（NetworkPolicy）是否放行
- **服务发现延迟**：检查注册中心心跳配置，排查客户端本地缓存是否过期
- **脑裂问题**：Zookeeper 集群奇数节点，检查 leader 选举日志

### 3. 应用服务故障

#### CPU 100%
1. `top` / `kubectl top pod` 定位高 CPU 进程
2. `top -Hp <pid>` 找出热点线程 TID
3. `printf '%x' <TID>` 转十六进制
4. `jstack <pid> | grep <hex_tid>` 找到线程堆栈
5. 分析是死循环、正则回溯还是 GC 过于频繁

#### 接口超时 / 响应慢
1. 检查数据库慢查询日志
2. 检查 Redis 连接池耗尽（ERR max number of clients reached）
3. 检查线程池队列堆积（监控 ThreadPoolExecutor activeCount/queueSize）
4. 检查下游接口调用链（Skywalking / Zipkin trace）

#### OOM
1. 配置 `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/tmp/dump.hprof`
2. 使用 MAT（Memory Analyzer Tool）分析 Heap Dump
3. 排查大对象、内存泄漏（如静态集合持有引用未释放、ThreadLocal 未 remove）

## 处理原则
1. **先止损，后排查**：优先恢复服务（重启、扩容、降级），再分析根因
2. **保留现场**：在重启前 dump 堆栈、日志，避免证据丢失
3. **逐层排查**：基础设施 → 中间件 → 应用代码，逐层排除
4. **写复盘报告**：记录时间线、根本原因、影响范围和改进措施
