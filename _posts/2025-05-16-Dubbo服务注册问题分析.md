## 问题现象

- 在Dubbo服务注册的过程中，当服务提供者启动后，本地nacos的控制台服务列表不存在服务提供者的注册信息。
- 但是服务调用是正常的

## 问题分析

关键日志
> [DEBUG] Using interface addresses to handle invocation, interface com.wkb.yl.service.YlDistribContentService, total address size

这句话表明：Dubbo 确实是通过注册中心进行的远程调用，而不是 injvm 本地调用

调用链路中，Dubbo 实际上找到了服务提供者的地址，能够正常发起 RPC 调用。问题在于**服务注册**阶段出现异常，提供者的信息没有成功写入 Nacos 注册中心。

## 根本原因分析

### 可能原因 1：Nacos 注册地址配置错误
服务提供者的 Dubbo 配置中，注册中心地址指向了错误的 Nacos 实例（如开发环境和本地 Nacos 混用），导致注册成功但在错误的命名空间（Namespace）或 Group 下。

### 可能原因 2：Nacos 命名空间 / Group 不匹配
提供者注册到了 namespace A，消费者从 namespace B 发现，二者不同但由于消费者有本地缓存，服务调用依然成功。检查 `spring.cloud.nacos.discovery.namespace` 配置。

### 可能原因 3：网络策略（防火墙 / NetworkPolicy）阻断注册
容器环境下，服务可以调用（已有缓存路由），但新的注册请求被防火墙拦截，导致注册失败而调用正常的"假象"。

### 可能原因 4：Dubbo 注册重试机制
 Dubbo 注册失败后会进入重试队列，注册动作是异步的。短暂的 Nacos 不可用会导致控制台暂时看不到服务，但 Dubbo 本身已通过缓存的 Provider 列表完成调用。

## 解决方案

1. **统一配置检查**：确认提供者和消费者的 Nacos 注册中心地址、namespace、group 完全一致
   ```yaml
   dubbo:
     registry:
       address: nacos://127.0.0.1:8848
       parameters:
         namespace: dev  # 确保与消费者一致
         group: DEFAULT_GROUP
   ```

2. **查看 Nacos 注册日志**：在服务提供者日志中搜索 `Register: URL` 关键字，确认注册请求是否发出以及是否成功

3. **检查 Nacos 控制台命名空间**：Nacos 控制台默认显示 public 命名空间，切换到对应命名空间再确认服务是否存在

4. **网络连通性验证**：在容器内 `curl http://<nacos-host>:8848/nacos/v1/ns/service/list` 确认 Nacos API 可达

## 经验总结

> 服务可以调用但控制台看不到，大概率是**命名空间/Group配置不一致**或**注册到了不同Nacos实例**。Dubbo的异步注册重试机制会掩盖注册失败，导致问题难以发现。建议在微服务启动脚本中加入注册成功的健康检查断言。
